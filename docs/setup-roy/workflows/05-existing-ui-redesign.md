# Workflow 5 — Redesign an existing interface

Use for a requested redesign or substantial improvement to an existing interface. Keep the scope to the screens or components requested. One request = one run.

1. Read `frontend-design` and `emil-design-eng` skills, inspect the affected UI and relevant project guidance, and treat the brief and existing product decisions as constraints.
2. Use `frontend-design` to propose and critique a specific visual direction before implementation. Resolve conflicts with the existing design system; update its owning documentation if shared rules change.
3. Implement the requested scope without changing product behavior unless asked. Follow `emil-design-eng` for component feedback and motion; preserve accessibility, responsive behavior, reduced-motion support, and relevant UI states. Use its required Before/After/Why table for UI code review findings.
4. Run `break-ui` only when worst-case testing is requested. Follow its full protocol and stop after reporting findings; fix them only when asked.
5. Report the implemented scope, key design decisions, documentation changes, and unresolved findings. Do not claim a review or implementation that was not performed.
